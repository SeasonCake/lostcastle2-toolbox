# LC2 本地 MOD 总库清点与接入边界（2026-08-28）

> 历史快照：记录当日清点结果；当前收录、作者、来源和分发状态以现行 catalog 与第三方说明为准。

## 1. 范围与结论

清点目录：`<local-mod-library>`。检查未移动、删除、覆盖或启动其中任何程序；受管接入只把精确 DLL 复制到被 Git 排除的本地生成目录，不回写来源包，也不改写已经发布的 v1.6.0。

2026-08-30 最后检查时，目录包含 72 个压缩包、9 个顶层裸 DLL、2 个外置 EXE、2 个顶层说明 TXT，另有 1 个源码目录，共 86 个顶层路径。新增的 `LostCastle2MaxPlayers16.dll` 是从已冻结 40 MB 整包中提取并校验的本机最小来源；原整包未覆盖或删除。统一静态识别器继续拒绝把整套 BepInEx/覆盖安装当作普通 MOD。

默认社区目录现纳入 53 个条目、54 个必要文件、`3,391,437` 字节；旧版重复、未完成、半成品和明确有 bug 的来源通常不进入默认列表。游戏内伤害统计由 1.5.1 原位升级为最新 1.6.4，不并列保留旧版；终始武器包的两个变体按 BepInPlugin 版本与精确哈希只选择 1.5.0“切换武器消失”载荷。新增的战利品 V2.4.0 与已收录 V2.5.3 同插件身份，且来源明确标注“有 bug”，因此不降级替换。“我不是药神”因作者本轮明确选择而作为例外纳入，但名称与使用说明始终保留“测试版”，真实游戏兼容性不外推。新增多人扩容只纳管 15,872 B 功能 DLL，不携带原包框架与生成 cfg。v1.6.0/v1.6.1 已发布资产不回写。

结论：总库的大多数内容复用同一套“一键安装/卸载”底座，但不会把任意压缩包直接覆盖到游戏目录。安全可维护单位是“单一固定 BepInEx 运行时 + 独占插件目录 + 逐文件清单 + 哈希 + 作者/使用说明”；跨目录配置默认不覆盖，让插件首次启动生成自己的配置。当前 53 项受管载荷中没有 Doorstop、coreclr、cache、interop、BepInEx 路径或生成 `.cfg`。

目录顺序由来源清单中的 `sort_priority` 维护：灵魂石、金币两个原有工具仍在最前；社区条目当前先显示玩家/队友数值、LC2 增强计划、资源转移、刻印灵魂石、自动复活、多人修复和动态血量。海克斯强化药水按实战价值排在前段，但使用说明明确它与三项现有 MOD 共用 F1；暴击字体改紫色属于纯视觉调整，排在功能/信息工具之后及其他外观类之前。排序只表示查找便利，不表示未经真实游戏运行的第三方逻辑已获得兼容性认证。

### 实时监测参考与怪物血量结论

- 自有战斗 HUD 曾静态研究第三方“游戏内伤害统计 1.6.4”的多人身份发现、官方统计锚点、逐 hit 兜底、去重和重连分段；只借鉴数据源分层思路，没有复制其累计值、倍率校准、持久化状态或 UI。自有单人伤害仍以游戏官方事件、结算页面和多轮真实对局校准；2P–4P 尚未完成真实校准。
- “玩家实时属性与队友面板 2.0”读取的是本地/队友玩家属性，静态界面字符串为玩家生命、攻击、暴击、元素等字段，不是怪物血量面板。
- “关卡动态血量 4.3.0”会修改怪物/Boss 的最大生命和相关倍率，F3 面板用于配置倍率；它不是显示怪物当前/最大生命的监测 MOD。
- 对当前 53 项受管目录及 `LCMods` 的相关文件名与 .NET 用户字符串复核后，尚未确认独立的“显示怪物当前/最大血量数值”社区 MOD。游戏自带 Boss 血条不计作此类 MOD；若以后取得专用插件，应作为新功能族单独登记和实测。

## 4. 当前安装合同

1. 目录只接受 catalog 中登记的 MOD，按文件大小与 SHA-256 双重校验。
2. 单 DLL 插件目标固定为 `<游戏目录>/BepInEx/plugins/<mod-id>/<filename>`；不同 MOD 不共用目录。
3. 压缩包只允许提取登记的单个文件名；catalog 拒绝压缩包成员路径穿越。
4. 卸载只删除该 MOD 的登记文件，并仅在自有目录为空时删除目录；不触碰其他插件。
5. 未定位游戏时失败关闭；全新环境首次安装 DLL MOD 时先明确询问是否初始化固定 BepInEx/Bridge，不从用户 MOD 包猜测或复制框架。检测到不同核心时零写入阻断。
6. 外置工具仍安装到工具箱 `managed_mods`，不会写入游戏插件目录。
7. 整包 BepInEx、资源替换包和多文件插件必须建立各自的文件所有权清单后再接入。

## 5. 后续纳管顺序

按风险从低到高推进：

1. 裸 DLL 和单 DLL 压缩包：提取程序集名、版本、作者、快捷键、依赖及精确哈希。
2. 多文件插件：冻结完整成员表、目标路径、配置保留策略和卸载边界。
3. 互斥/冲突元数据：至少覆盖相同快捷键、同一 Harmony 目标和共享配置文件。
4. 整包框架与资源替换：单独设计备份/恢复，不与普通插件共用“一键删除”。
