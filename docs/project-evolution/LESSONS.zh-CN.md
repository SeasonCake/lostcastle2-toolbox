# 可复用工程经验

## 1. 先建立数据链，再讨论“看起来对不对”

对映射敏感的功能固定追踪：

`game source -> identity/slot -> session -> protocol -> aggregator -> UI`

每层记录字段名、单位、默认值、缺失行为、去重键和回退条件。数字接近只能产生假设；逐槽身份、房间守恒与最终官方值才构成可证伪证据。

## 2. 实时值和最终值必须是两种状态

- 局中过程值解决及时反馈，结算值解决权威对账；二者不能用“取最大值”或倍率偷偷合并。
- 最终值可能比过程值高，也可能更低。UI、状态机和测试都必须允许双向校正。
- 当身份不完整、事件被跳过或数据源停滞时，宁可明确降级，也不要把猜测包装成精确值。

## 3. 自动测试不能替代真实多人

- known-good 证明正常路径，known-red 证明检查器真的能抓住历史故障；两者缺一不可。
- 单人退出后继续冒险、roster 收缩或旧房迟到回调，可能让“同一张截图”实际跨越不同会话语义。
- 一个样本只证明一次复现。宿主/客机、延迟、掉线、召唤、变身、NPC、自然结算和房间切换应拆成独立门。

## 4. 会话生命周期比累计公式更容易造成灾难性错误

- 新 session 必须原子清空身份、累计、降级状态和冻结 final。
- superseded、recovered、normal final 与退出路径不能共用“当前全局摘要”。
- 任何跨局文件都必须能交叉验证自己的 session；无法证明时拒绝归档，不拼接。
- 正式产品若不需要历史分析，优先只保留内存状态。高频 journal 和每局 ZIP 会把调试便利变成用户磁盘风险。

## 5. 探针必须有退出策略

- 诊断代码先定义收集字段、频率、隐私边界、正负控制和删除/关闭条件。
- 高频探针默认关闭；正式版只保留启动、版本、连接、队列溢出和明确错误等低频支持信号。
- 探针 PASS 只说明观察面成立，不自动授权它进入产品数据流。

## 6. UI 验收要看实际表面

- 源码字符串、隐藏渲染或 import 通过不等于可见正确。
- 对紧凑 HUD 和桌面窗口，至少检查常用 DPI、长数字、多人、降级、官方结算、空/错/断开状态，以及窗口几何和字体测量。
- 短标签服务操作速度，详细解释放在完整界面；内部 Hook、HMAC、cache 等实现词不应进入日常 UI。

## 7. 包身份是一条独立证据链

- source、build、package、desktop、installed、ZIP、upload/readback 是不同阶段，任何一个 PASS 都不能替代下一阶段。
- 分享包必须从干净候选生成，确认配置为 0、测试导出目录不存在、文件数/字节/哈希一致，并验证解压后的入口和运行时。
- “本机已有依赖能运行”不能证明新用户能运行；必须用无 BepInEx 的隔离夹具验证首次安装和二次幂等。

## 8. 第三方载荷保留来源，不混淆作者与上传者

- 最小载荷、作者证据、上传来源、版本冲突、依赖、SHA-256 和分发决定分别记录。
- 程序/源码/随包说明中的明确作者优先；上传者只作来源，不自动变成作者。
- 第三方代码默认不启用，安装冲突要停止并提示，不能盲目覆盖不同身份的运行时核心。

## 9. 公开工程档案应保留结论，去掉本机生活痕迹

- 保留版本批次、失败数字、假设如何被推翻、最终修复与 NOT RUN；这些是未来项目最有价值的部分。
- 去掉个人用户名、绝对路径、玩家昵称/账号、聊天、网络地址、未经筛选的日志和配置；公开作者署名与已确认的社区来源别名按角色保留。
- 用稳定别名与相对路径保证可复现；用短摘要代替几十 MB 原始数据。
- 历史 checkpoint 必须标注“时间点记录”，避免后续读者把旧状态当成当前真相。

## 10. 发布裁决使用四类归档

每轮收口把发现归入：

1. 实际结果失败；
2. 当时规则违规；
3. 后来新增教训；
4. 规范落地后回归。

这样既不会把历史失败抹掉，也不会让已经失效的旧规则永久阻断当前版本。最后再明确列出 `NOT RUN`，让读者知道结论的边界。
