# LC2 启动性能三臂实测结果

本文件是 2026-08-27 启动性能实验的长期维护记录；测试状态切换脚本与检查点保留在本地 `artifacts/startup-performance/2026-08-27-three-arm/`。

## 结论

- 旧三臂样本证明白/黑空白阶段不是 LC2 Combat Bridge 独有，但当时没有冻结显示模式；后续往返复核证明“长白屏”强依赖窗口模式，旧结论不能外推到当前“窗口化全屏”。
- 暖启动样本中，BepInEx-only（B）到主菜单的中位上界约 `22.71 s`，原版（A）约 `16.46 s`，差约 `+6.25 s`。首轮 A 冷启动本身约 `23.24 s`，因此该差值只适用于本次暖缓存序列，不能外推到所有机器。
- Bridge 0.3.0（C）没有形成 B 组之上的可见启动回归：C 的有效视觉样本中位上界约 `20.97 s`；Chainloader 中位数仅比 B 高 `22 ms`，低于本次日志轮询和批量写入能够可靠分辨的尺度。
- 当前数秒级启动增量的首要归因是 BepInEx/Il2CppInterop 启动链，而不是 Bridge 0.3.0 的 `PatchAll`。产品级“普通启动无感”门仍未通过，但 Bridge 自身的相对启动门通过。
- 退出残留是独立问题：BepInEx-only 与 Bridge 组都观察到主窗口关闭后控制台/进程残留；一个原版样本也出现过无窗口进程残留。现有样本不能把退出问题归因给 Bridge。

## 测试身份与方法

- 日期：2026-08-27（Asia/Shanghai）。
- 顺序：三轮拉丁方 `A-B-C`、`B-C-A`、`C-A-B`；另补一次 C 组视觉复测。
- A：原版，不加载 BepInEx。
- B：BepInEx/Il2CppInterop，禁用 Bridge。
- C：BepInEx/Il2CppInterop + Bridge 0.3.0。
- 所有时间都换算为 `LostCastle2.exe` 实际进程创建后的毫秒/秒，排除 Steam/启动器请求到进程创建之间约 `3.3–11.9 s` 的不稳定等待。
- `Window`、`Chainloader`、`Plugin`、`Scene` 与无响应来自进程/日志轮询；主菜单来自固定时点的真实窗口截图。截图只能给出区间或上界，不能伪装成逐帧精确值。
- A1 首次监控命中了一个提前退出的进程代际，故其进程标记无效，只保留经人工复核的视觉时间；C3 定时截图时窗口未前置，故其视觉时间无效，另用 C-visual 补测。

## 白屏与退出问题

1. A1 原版、B3 与 C 旧视觉样本都记录到空白阶段，但这些样本没有把窗口模式作为实验变量，因此只能排除“Bridge 是白屏必要条件”，不能说明每种显示模式都会出现同样的白屏。
2. 作者完成往返复现：最大化窗口出现明显长白屏；改为“窗口化全屏”后肉眼白屏消失；切回后再次出现。显示模式是目前最强、可重复的触发变量。
3. 2026-08-27 复核时，两份 `GameSettings` 均保存 `mFullScreenMode=2`，游戏界面对应“窗口化全屏”。在不主动激活游戏窗口的被动启动中，截图仍于进程约 `7.14–7.31 s` 捕获到白色初始化表面，并在约 `7.48 s` 前转黑；它只有数百毫秒量级，与“肉眼白屏消失”一致。
4. 同次被动样本中 Plugin/Chainloader 约 `7.327 s`、Scene ready 约 `8.693 s`。白色表面切换时间与 Chainloader 接近，但这只是相关性；显示模式决定它是否、以及多长时间暴露给用户，不能据此归因给 Bridge。
5. B3、C2、C 视觉复测在主窗口关闭后仍保留 BepInEx 控制台/游戏进程；关闭唯一控制台后退出。A2 也出现过无窗口残留，所以需要单独设计退出延迟采样，不能把它混入启动结论。

当前白屏验收基线：保持界面“窗口化全屏”和实存值 `2`；不主动前置未完成渲染的窗口；以用户实际可见的连续长白帧为失败。此前一次强制激活窗口后捕获的白帧属于测试干预，不纳入裁决。
